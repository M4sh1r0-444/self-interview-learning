# 1.3w字，23 道 Prompt 工程面试题总结

大家好，我是 Guide。准备这个项目的面试时，Prompt 部分值得讲到代码层面：题目数量怎么控制，模型返回的 JSON 怎么校验，简历里混入指令怎么办。这些问题都能顺着项目里的调用链继续追问。

另外，对弈 Prompt 基础概念可以先看 [大模型提示词工程实践](https://javaguide.cn/ai/agent/prompt-engineering.html)。

## Prompt 模板与出题
### 如何管理和组织 Prompt？
项目把出题、评估、简历分析、知识库问答等场景的模板放在 `app/src/main/resources/prompts/`，使用 StringTemplate `.st` 文件。多数场景拆成 system 和 user 两份，例如方向出题使用 `interview-question-skill-system.st` 和 `interview-question-skill-user.st`。

system 模板描述面试官职责、出题标准和输出要求；user 模板传入本次题量、难度、分类分配、历史知识点和参考题库。评估场景有自己的模板，避免把出题要求带进评分过程。

`InterviewQuestionService` 在构造时读取模板，调用时通过 `render(variables)` 填入本次参数。模板加载方法如下：

```java
private static PromptTemplate loadTemplate(ResourceLoader loader, String location)
    throws IOException {
  return new PromptTemplate(
      loader.getResource(location).getContentAsString(StandardCharsets.UTF_8));
}
```

模板文件化便于单独审阅提示词、查看 Git 差异，也减少了 Java 字符串拼接。但当前模板随应用打包，服务启动时加载，**没有热更新能力**。修改 `.st` 后仍需重新打包、部署，已经创建的 `PromptTemplate` 不会自动刷新。

现在用 Git 管理模板就能追踪变更。以后要做在线实验，再考虑给模板增加版本号、灰度配置和回滚入口。只把字符串搬进数据库，还不足以保证一次实验能复现。

### 文字出题为什么拆成简历题和方向题？两路都会调用工具吗？
简历题用于追问候选人做过的项目；方向题用于覆盖所选岗位的技术知识。两者依赖的材料不同：简历题要求项目、技术栈和场景都能在简历中找到依据，方向题则按分类分配表和参考题库生成。

有简历时，`InterviewQuestionService` 按约 60% 简历题、40% 方向题分配主问题，通过 `CompletableFuture` 和虚拟线程并行调用。例如请求 10 道主问题，会分成 6 道简历题和 4 道方向题。两批结果合并时，还要调整问题索引及追问的父问题索引。

当前两路都使用：

```java
ChatClient questionChatClient =
    llmProviderRegistry.getPlainChatClient(llmProvider);
```

这个客户端不注册 Skill 工具、对话记忆和日志 Advisor，只按配置注册 `SafeGuardAdvisor`。后端先读取 Skill 的 persona、分类和 references，再把材料放进 Prompt。方向题的 system 模板也明确要求直接基于已提供的内容出题，不调用工具。

文字出题使用的 Skill 材料由后端确定。对于一次返回完整 JSON 题单的任务，预加载可以省去工具调用的额外往返，也便于检查究竟给模型传了什么。语音面试则保留了按需调用 Skill 工具的方式。

### 一份出题 Prompt 应该写清哪些要求？
项目里的要求主要围绕出题材料、题量和题目用途展开。简历题限定只能询问简历中明确提到的经历；方向题传入分类分配表；没有简历时，额外禁止使用暗示已经读过简历的措辞。

例如，简历只写了使用 Redis 做缓存，就可以询问缓存更新、过期策略、故障处理。要追问某次 Redis 集群扩容，得先确认简历确实提到了这段经历。否则，题目已经替候选人编出了一个项目背景。

负向约束指出不允许发生的行为，正向要求则说明缺少信息时该怎样继续。比如在禁止虚构经历之外，还可以补充以下要求，这是改进示例：

```latex
围绕简历明确提到的项目和技术提问。
缺少部署规模、性能指标等信息时，先询问候选人，不自行补全。
每次追问选择一个具体问题，例如技术选型依据或故障排查过程。
```

角色描述只需与任务有关。写出面试方向、候选人级别、考察内容和评分标准，比不断增加“资深”“顶级”等形容词更容易检查效果。

模板本身也可能出现不一致：当前方向题要求 `topicSummary` 在 10 字以内，但部分中英文混合示例明显更长。模型既看规则，也看示例，这类冲突应通过统一长度口径、缩短示例来消除。

### 要求恰好生成 N 道题，为什么还需要业务代码处理？
Prompt 中的数量要求可能被模型遗漏。项目的 `QuestionListDTO` 只定义了 `List<QuestionDTO>`，并没有根据本次请求动态生成数组长度约束。即使结果通过 JSON Schema 校验，也可能少于要求的题数。

题目转换后，`capToMainCount()` 按主问题数量处理：超过要求时截断，并保留入选主问题的追问；不足时原样保留，记录 warning。请求 10 道、返回 8 道时，这个方法会返回 8 道，**不会自动补齐缺少的 2 道**。

分类分配与实际结果也要分开看。`InterviewSkillService.calculateAllocation()` 先给保底分类分配名额，再覆盖其他分类，并优先分配核心分类。分配表会传给模型，但当前出题方法没有逐类核对生成结果。模板中的基础、进阶、专家比例也是生成要求，现有 `QuestionDTO` 没有独立的难度字段，无法直接按字段统计实际比例。

如果产品必须满足精确题量和分类配额，可以在转换后统计缺口，只对缺少的分类补生成，并限制补生成次数。当前尚未实现这一步。

### 如何避免重复出题？
项目要求每道主问题生成 `topicSummary`，下次出题时把历史知识点按 `type` 分组后传入。历史数据没有摘要时，`buildHistoricalSection()` 会截取问题前 30 个字符作为替代。

这样比把所有完整问题塞回 Prompt 更省空间，模型也容易看到已考过哪些知识点。不过，这仍然依赖模型遵守去重要求。比如“HashMap 扩容机制”和“HashMap resize 过程”可能考察同一知识点，换个摘要名称仍会重复。

当前并行出题的两路只共享已有历史，看不到对方本次正在生成的题目，因此合并后的题单也可能重复。进一步改进时，可以先按知识点标识或规范化摘要去重，再对疑似重复题做语义比较；单纯比较题目全文是否相等，只能发现完全相同的表述。

### 提供示例时，怎样避免模型照搬示例中的事实？
示例适合说明输出格式和回答粒度，但示例中的数字也会影响生成结果。简历分析模板要求关注量化产出，并举了响应时间、QPS 等例子。候选人的简历缺少这些数据时，模型可能把示例数字写进修改建议，读起来就像已经取得的成果。

可以在示例中区分已知事实和待补信息，以下是建议写法：

```latex
已知信息：用 Redis 缓存商品详情，减轻数据库查询压力。
优化建议：补充缓存更新方式、过期策略，以及实际测量的命中率或延迟变化。
没有测量数据时，不填写 QPS、命中率和提升倍数。
```

候选人没有提供测量数据时，输出可以停在补充材料的建议上，不必强行生成一段带数字的成果描述。

## 结构化输出与失败处理
### 结构化输出怎么保证可靠性？
项目用 `BeanOutputConverter` 根据 DTO 生成格式说明和 JSON Schema，再由 `StructuredOutputInvoker` 统一调用模型、处理失败。Spring AI 的 converter 负责给出格式指导和解析结果，本身不能保证模型遵守要求，官方也明确说明了这一点。参见 [Output Converters](https://docs.spring.io/spring-ai/reference/api/structured-output/converters.html)。

当前默认开启 `structured-schema-validation-enabled`，实际执行的是：

```java
var call = chatClient.prompt()
    .system(systemPrompt)
    .user(userPrompt)
    .call();

if (schemaValidationEnabled) {
  return call.entity(outputConverter, spec -> spec.validateSchema());
}
String content = call.content();
return convertWithRepair(content, outputConverter, logContext, log);
```

这段代码对应两种处理方式：默认路径使用 Spring AI 的 Schema 校验及失败纠正机制；关闭开关后，项目直接解析文本，解析失败时尝试修复字符串里未转义的双引号，再解析一次。本地引号修复只针对一类格式错误，默认开启 Schema 校验时不会执行这个分支。

返回结果还要经过业务检查。JSON 可解析、字段类型正确，只能说明结构符合要求；项目名称是否来自简历、主问题是否够数、分类是否正确，都需要另外判断。

### 解析失败后怎么重试？最多会调用几次模型？
`StructuredOutputInvoker` 外层默认最多尝试 2 次，包括首次调用。第二次调用会在 system prompt 后面追加格式修正要求，可配置是否携带上次异常信息。异常文本会折叠成单行，默认截取前 200 个字符，避免过长错误信息进入 Prompt。

这里的外层重试会重新请求结果，并没有把上一次完整 JSON 发回模型做定点编辑。它捕获调用过程中的 `Exception`，服务调用失败也会进入这个分支。排查“结构化解析失败”日志时，还得检查原始异常类型。

默认开启的 `validateSchema()` 自己也有校验纠正循环。框架会在校验失败时把错误信息补进用户消息，再次调用模型；项目外层追加错误到 system prompt，两者是不同机制。参见 [Schema Validation & Self-Correction](https://docs.spring.io/spring-ai/reference/api/structured-output/validation.html)。

所以 `structured-max-attempts: 2` 只限制项目外层循环，不能直接推导为最多两次模型请求。排查延迟和费用时，要同时看框架校验重试、项目重试及模型客户端的请求重试。项目的 `app.ai.structured_output.attempts` 指标记录的是外层尝试，也不能直接当作供应商请求次数。

后续可以统一重试预算，并区分可重试的服务异常、格式失败和明确的业务失败。错误信息进入 Prompt 前，也应避免回传原始简历或模型输出中的大段内容；折叠换行和截断长度不等于脱敏。

### BeanOutputConverter 和模型原生结构化输出有什么区别？
两者可以配合使用。`BeanOutputConverter` 提供类型对应的 Schema 和转换能力，原生结构化输出则把 Schema 通过供应商 API 参数传给模型服务，约束生成格式。Spring AI 提供 `useProviderStructuredOutput()` 开关，但需要核实所选供应商、模型和 Schema 特性是否受支持。参见 [Provider-Native Structured Output](https://docs.spring.io/spring-ai/reference/api/structured-output/native.html)。

当前 `StructuredOutputInvoker` 显式启用了 `validateSchema()`，没有调用 `useProviderStructuredOutput()`。目前采用的是格式提示、返回结果校验和重试。

即使启用原生结构化输出，简历中没有的项目也可能出现在一个完全合法的 JSON 里。事实核对和业务规则校验仍然要保留。

### AI 调用失败后，项目怎样降级？
项目根据场景保留可用结果，或切换到其他生成方式：

| 场景 | 当前处理 |
| --- | --- |
| 查询重写失败 | 使用原问题继续检索 |
| 检索无命中 | 返回固定话术，跳过回答生成 |
| 评估汇总失败 | 使用已经完成的批次评估结果聚合反馈 |
| 简历题抛异常 | 尝试重新生成全量方向题 |
| 方向题抛异常、简历题已有结果 | 返回已有简历题，不保证补足总题量 |
| 方向题返回空题单 | 生成默认题目 |


出题默认题目优先按 Skill 分类生成通用问题；没有分类时，才使用代码里的固定题目数组。`generateDirectionOnly()` 会继续抛出 `BusinessException`，所以结构化调用耗尽重试后，也并非所有路径都会自动降级成功。

是否允许少题返回、是否要提示正在使用默认题目，属于产品行为，需要和接口返回、前端展示一起确定。

## RAG 与上下文
### RAG 场景下的 Prompt 怎么设计？
项目把检索查询改写和回答生成分成两次任务。查询改写输出单行检索文本，回答生成接收原始问题及检索片段。

查询改写适合补全追问。例如上一轮在讨论 Redis 持久化，用户继续问两种方式怎样取舍，改写时就需要带上历史上下文。`knowledgebase-query-rewrite.st` 要求保留原意、不引入新事实，已经足够具体的问题可以原样输出。

`KnowledgeBaseQueryService` 默认先用改写后的查询检索，未命中时再尝试原问题。它也提供双路召回融合开关 `mergeOriginalQuery`，默认关闭；开启后两路分别检索，按文档 ID 去重、保留较高分，再取最终 Top K。

检索参数按原始问题去空白后的字符数分档，默认值如下：

| 原始问题长度 | Top K | 最低相似度 |
| --- | --- | --- |
| 不超过 4 个字符 | 20 | 0.25 |
| 5～12 个字符 | 12 | 0.28 |
| 超过 12 个字符 | 8 | 0.28 |


这些是当前配置的起点。短查询多召回一些片段，可以扩大候选范围，也会增加无关内容；阈值是否合适，要看固定样本上的检索结果，不能仅凭查询长短判断质量。

回答阶段用独立模板要求模型依据片段回答，信息不足时明确说明，来源冲突时保留冲突。user prompt 中用分隔符包裹文档，再提供用户问题，减少文档正文与任务要求混在一起的情况。

### 检索为空时，为什么由代码直接返回？
没有检索片段时，继续让模型回答会增加无依据补充的机会。项目在检索后调用 `hasEffectiveHit()`，当前实现只判断列表是否非空；相似度阈值由前面的向量检索处理。

未命中时返回：

> 抱歉，在选定的知识库中未检索到相关信息。请换一个更具体的关键词或补充上下文后再试。
>

这会省去回答生成调用。启用查询改写时，检索前仍可能发生一次 LLM 调用。

流式回答还会缓冲开头约 120 个字符，检查是否出现预设的信息不足短语，命中后替换成固定话术。这个探测窗口用于统一拒答表达。例如，有用回答中只是提到了信息不足，也可能被关键词规则误判，所以测试还要覆盖正常回答被截断的情况。

### 如何让回答带上可核对的来源？
当前工作区的 `RagSources` 会给实际传入 Prompt 的片段编上 `[S1]`、`[S2]` 等编号，并附上可用的来源名称、文件名和片段序号。system 模板要求模型只使用已有编号，不编造页码或来源。

回答结束后，服务端根据同一批文档追加参考片段列表。列表不依赖模型自己编写，因此能够核对本次究竟给模型提供了哪些资料。

但这个列表只代表模型收到了这些片段。某句话是否确实得到 `[S2]` 支持，仍需检查答案与片段的对应关系。

### Prompt 太长时，怎么控制上下文？
不同场景需要保留的信息不同。评估服务 `UnifiedEvaluationService` 将简历限制到前 3000 个字符，参考基线限制到前 6000 个字符，超过后附加截断提示。这能约束输入规模，也可能丢掉简历末尾的重要项目。

查询改写只把每条历史 assistant 消息截到 200 个字符，历史 user 消息并没有在这个方法里同样截断。RAG 的 `RagSources.context()` 则直接拼接入选片段，没有额外的总 Token 预算。Top K 限制了片段数，却不能保证整个请求一定装得进模型上下文。

规划预算时，要给输出和可能发生的工具交互预留空间，再统计 system prompt、格式说明、当前问题、历史消息和检索片段。裁剪时可以按相关性删除低价值片段，并避免截断到只剩一半代码或一句话的前半截。这个总预算方案尚未统一落到当前 RAG 链路。

这里的字符数也不能直接换算成固定 Token 数。中文、英文、代码和不同分词器的比例不同；现有字符上限适合粗略控制长度，精确预算需要结合实际模型的分词方式与 usage 数据。

## 语音面试
### 语音面试的 Prompt 和文字出题有什么不同？
文字出题一次生成整套题单，语音面试每轮只需要一段适合播报的问题。`VoiceInterviewPromptService` 的当前要求包括：每轮一个主问题，必要时最多一个短追问；总长控制在 2～4 句；避免列表、Markdown 和代码块；候选人要求换题时切换方向。

简历不为空时，服务会先净化简历文本，用随机分隔符包裹，再加入 system prompt。首轮要求用一句话说明已经查阅简历，随后进入第一个问题。

生成后的文本还会由 `DashscopeLlmService` 清理加粗、反引号、无序列表符号及多余空白。完整结果的长度上限取 `max(80, aiQuestionMaxChars)`，当前配置默认是 120 个字符；截断范围的后半段有句末标点时，优先在该处结束。

删除代码围栏后，语言标记和代码内容仍可能留下。这类清理无法把代码解释成口语，播报效果仍依赖生成阶段遵守输出约束。

### 语音面试为什么通过 Skill 工具加载角色？
语音客户端注册了 Skill 工具和 `ToolCallingAdvisor`。system prompt 先写入方向，并要求尚未加载完整角色时调用对应 Skill。工具返回的角色规则进入本轮工具交互上下文，供模型继续生成问题。

这种方式允许模型按需获取角色材料，但也多了一个不确定因素：模型可能跳过工具调用。当前 `VoiceInterviewPromptService` 只负责写入这条要求，不能据此确认角色已加载；配置了工具处理能力，也不代表模型必然使用工具。

角色规则必须在首轮生效时，可以像文字出题一样由后端预加载，或在编排层记录加载状态并处理失败。前者让角色材料在调用前就已确定，后者保留工具加载过程，但需要处理失败状态。选型时再对照首轮耗时决定。

### 长时间对话怎么避免历史越积越多？
项目已有 `VoiceContextCompressor`，默认采用 `SUMMARY` 模式，保留近期原文，并把更早轮次合并进滚动摘要。当前配置的窗口大小是 20 轮，未摘要的早期内容积累到 10 轮时触发一次摘要，历史字符预算为 12000，摘要上限为 4000。

两次摘要之间，尚未达到批次大小的早期轮次仍需保留，实际携带的原文可能超过 20 轮。超过字符预算时，代码会优先丢弃较早的近期记录；连最新一条也放不下时，截断副本并优先保留候选人回答的尾部，不修改原实体。

摘要模板要求保留候选人提到的项目、技术栈、经历和已答题点。摘要调用使用 plain client，避免工具调用和自动记忆重新引入额外材料。生成失败时保留旧摘要或退回近期窗口，继续受字符预算约束。

摘要也可能漏掉信息。测试时应关注它是否保留了已问知识点、候选人修正过的说法，以及下一轮追问所需的事实。这里的预算针对历史内容，完整请求仍会包含角色规则、简历和当前输入。

## Prompt 注入防御
### Prompt 注入与 SQL 注入有什么区别？
Prompt 注入是把攻击指令放进模型会读取的文本，诱导模型偏离原任务。用户直接在聊天框要求改变评分规则，属于直接注入；指令藏在简历、检索文档或工具返回内容里，属于间接注入。间接注入的区分依据是指令来自外部材料，并不要求最终用户一定不知情。参见 [OWASP LLM01: Prompt Injection](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)。

SQL 参数化查询可以让数据库把参数作为数据处理。自然语言 Prompt 中的角色、标签和分隔符，则需要模型理解并遵守。把简历放进 user 消息或模板变量，并没有获得类似 `PreparedStatement` 的语法隔离保证。

在本项目里，候选人可能把修改评分标准的要求写进简历。应用应把它视为简历内容，评分标准仍由受信任的系统规则决定。是否真的做到这一点，要用包含恶意内容的样本验证。

### 项目已经做了哪些防御？还存在哪些不足？
`PromptSanitizer` 在部分直接拼接点执行正则替换，处理行首角色标记、若干中英文注入短语、伪造的静态分隔符和 `data-boundary` 标签。语音简历、部分 JD 和拼接输入会经过它；模板插值点没有统一执行相同的净化流程。

`PromptSecurityConstants` 提供防注入说明。结构化调用、知识库回答和语音 system prompt 等路径会追加这些规则，强调外部材料应当作为数据处理。查询改写等只使用 user prompt 的路径，采用的是模板中的数据说明，覆盖方式并不完全相同。

客户端还按配置加入 `SafeGuardAdvisor`，对请求文本做敏感短语匹配，命中后直接返回固定话术。它能拦截已知表达，无法覆盖所有语义相同的改写。

这些措施可以降低风险，但模板包裹不构成免检理由，正则过滤也不能保证保留所有正常内容。当前还没有统一的输出安全检查；JSON Schema 校验解决的是格式问题，不能判定模型有没有遵从恶意评分指令。

### 正则净化怎样减少误伤？随机分隔符能保证安全吗？
当前角色标记规则锚定行首，减少对普通技术描述的干扰；注入短语匹配完整表达，避免单独过滤常见词。分隔符规则则清理项目正在使用的标记形式。

但正常文档也可能讨论 Prompt 注入，其中自然会包含攻击示例。直接删除这些文本会损失信息，因此净化规则需要同时测试恶意输入和正常引用场景。

`wrapWithDelimiters()` 用 UUID 的前 8 个字符生成标签，例如：

```latex
<data-boundary-a3f2c1b0-resume>
候选人的简历文本
</data-boundary-a3f2c1b0-resume>

```

随机化增加了攻击者预先构造相同结束标签的难度。但模型不会像 XML 解析器一样强制检查标签配对，攻击也不必依赖关闭标签。随机标签只是在文本中提示数据范围，模型仍可能遵从标签内部的恶意要求。

### SafeGuardAdvisor 检查的是用户输入还是模型输出？
它位于请求侧，但在项目实际依赖的 Spring AI 2.0.0 中，匹配对象是 `request.prompt().getContents()`。这个方法拼接 Prompt 内各条消息的文本，当前 user 消息、system 和已经加入请求的历史内容都可能参与匹配。

匹配使用 `String.contains()`，区分大小写。项目默认词表包含中英文的角色切换、忽略指令等短语，命中后返回固定话术：抱歉，我只能协助面试相关的任务。它没有在模型返回后扫描输出。

扩大词表前，要检查系统模板是否也会命中，以及知识库里的正常攻击示例会不会被拦截。`order(100)` 设置了它在 Advisor 链中的顺序；新增工具或记忆 Advisor 后，还需要检查后续请求中哪些消息会经过它。

固定拒绝话术还有一个工程影响：结构化接口期待 JSON，拦截后却可能收到普通文本。这个结果会被解析流程当作失败，触发无意义的重试。后续可以把请求拦截表达成可识别的业务状态，并让重试策略排除这类失败。

### 工具参数来自模型，就可以信任吗？
仍然需要验证。system prompt 指定了某个 Skill，模型生成的 `command` 参数依然可能受外部文本影响。参数经由模型生成，并不会自动变成可信输入。

项目使用的 `spring-ai-agent-utils 0.10.0` 会把注册的 Skill 保存到 Map，调用时通过 `skillsMap.get(command)` 查找。这限制了可加载的集合；输入路径字符串并不等于能读取该路径。

项目自己的 references 读取也有 `isSafeReferencePath()` 检查，会拒绝包含 `..`、以路径分隔符开头或不符合允许字符规则的路径。这部分检查限制了后端能够读取的引用路径。

可注册的 Skill 不一定都适合当前面试。进一步收紧时，可以按会话限定允许加载的 Skill，校验工具参数，并限制工具能访问的资源。扩展到文件写入、外部请求等工具时，还需要由程序决定可执行操作，不能只让模型阅读一段禁止越权的说明。

## Prompt 效果验证
### 修改 Prompt 后，怎样判断有没有改善？
先固定输入样本、模型和配置，保留改动前后的结果，再检查这次修改要解决的问题。出题可以统计数量达标率、分类偏差和重复题；简历题需要检查是否虚构经历；RAG 需要同时检查证据命中、回答依据和误拒答；语音摘要需要检查关键事实有没有丢失。

项目已经有 RAG 测评入口 `:app:ragEvaluation`，相关说明位于 `app/src/test/resources/rag-eval/README.md`。固定样本覆盖直接事实、同义改写、多轮追问、跨段问题和知识库外问题，并区分开发集与留出集。报告记录 Prompt hash、模型和配置，支持对照查看 Hit@K、证据召回、MRR、拒答指标与分阶段耗时。

这套测评会使用模型服务和独立数据库环境，需要按 README 准备后运行。当前报告里的回答忠实度仍需要人工复核，Token 用量也尚未完整采集。比较两版 Prompt 时，要明确哪些指标已经测得、哪些还缺数据。

准备面试时，可以选一组数量不足的题单、一组被错误改写的查询或一段丢失事实的语音摘要，说明修改了哪条规则、对照结果怎样、有没有引入新问题。没有测量结果时，就讲清机制和待验证项，不填写提升比例。
